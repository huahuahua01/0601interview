# 题目一：新增检测类别（Green Cone）

---

## 背景

公司目前已有一个基于 YOLO 的安全监控系统。

系统已经能够检测：

- Person
- Helmet
- Vest
- Vehicle
- Cone（Red / Orange，红色 / 橘色锥桶）

并已经完成训练和部署。

---

## 任务

现有模型已能检测常见颜色的锥桶（Cone）：

- Red Cone（红色锥桶）
- Orange Cone（橘色锥桶）

客户提出新需求：

系统需要新增检测以下目标：

- Green Cone（绿色锥桶）

要求：

- 尽可能复用现有系统
- 降低重新训练成本
- 保证上线周期最短

---

### 请回答

#### 1. 数据层面

你会如何收集训练数据？

需要多少数据量？

如何保证数据质量？

如何划分：

- Train
- Validation
- Test

**回答：**

我会优先采用“**复用现有红/橘色锥桶数据 + 补充少量真实绿色锥桶数据 + 数据增强**”的方式，而不是从零开始大规模采集。

- **如何收集训练数据**
  - 保留现有的 Red / Orange Cone 数据，尽量覆盖不同背景、角度、距离和光照；
  - 补充少量真实 Green Cone 图片，用来让模型学到“绿色锥桶”的真实外观；
  - 对红色锥桶样本做颜色迁移和几何增强，作为绿色锥桶的冷启动样本。

- **需要多少数据量**
  - 真实绿色锥桶样本不必一开始就很多，建议先有几百张左右的可用样本；
  - 如果时间紧，可以先用少量真实样本 + 大量增强样本完成第一版；
  - 后续上线后再收集误检、漏检和难例，继续迭代。

- **如何保证数据质量**
  - 去重，避免同一视频连续帧同时进入训练集和测试集；
  - 检查标注框是否紧贴目标，避免框太大或漏标；
  - 确保不同场景都被覆盖，比如白天、夜晚、逆光、复杂背景；
  - 绿色锥桶样本不能只集中在一种背景下，否则容易过拟合。

- **如何划分 Train / Validation / Test**
  - 一般可按 7:2:1 或 8:1:1 划分；
  - 更重要的是按“视频/场景级”划分，而不是单帧随机划分，避免数据泄漏；
  - Test 集尽量保留最接近真实线上场景的数据，用来验证最终效果。

##### Coding 任务：数据增强

在已有红色锥桶数据的基础上，通过颜色变换与几何增强，低成本扩展绿色锥桶训练样本。

**回答：**

我已经实现了 `task1/data_color_aug.py`，核心思路如下：

1. **颜色变换实现思路**
   - 先把图像从 BGR 转到 HSV；
   - 在 HSV 空间里找到红色区域；
   - 将红色区域的 hue 平移到绿色附近；
   - 再转回 BGR，得到绿色锥桶图像。

   这样做的好处是：HSV 更适合做颜色迁移，因为色相、饱和度、亮度是分开的，不容易破坏图像结构。

2. **2^N 组合生成逻辑**
   - 我把增强变换看成 N 个二值开关；
   - 每种增强都可以“开/关”两种状态；
   - 所以组合总数是 `2^N`；
   - 对每张输入图先做颜色变换，再遍历所有增强组合，最终输出 `10 × 2^N` 张图。

3. **输出数量约束**
   - 如果输入目录里有 10 张图片，增强种类数为 N，那么输出图片总数应为：
     - `10 × 2^N`
   - 脚本会自动打印实际输出数量，便于核对。

4. **交付说明**
   - `output_images/` 中图片数量应符合预期；
   - 文件名带有增强组合编码，方便追踪每张图是如何生成的。

#### 2. 标注层面

如何进行数据标注？

如何制定标注规范？

如何保证多人标注一致性？

**回答：**

- **如何进行数据标注**
  - 对锥桶进行目标检测标注（bounding box）；
  - 新增 `Green Cone` 类别，并与原有 `Red Cone / Orange Cone` 区分开；
  - 如果后续还要更精细地识别颜色，可以在检测框基础上增加颜色属性标签。

- **如何制定标注规范**
  - 锥桶主体可见面积足够大时才标注；
  - 严重遮挡、无法判断颜色时标为 `ignore` 或 `unknown`；
  - 颜色判定以主体主色调为准，不要被局部高光或阴影干扰；
  - 标注框尽量紧贴目标边界，避免过松或过大。

- **如何保证多人标注一致性**
  - 统一标注手册和样例图；
  - 关键样本进行双人交叉标注；
  - 对有争议的样本由仲裁人员统一裁定；
  - 定期抽检标注结果，统计一致率并修正偏差。

---

#### 3. 模型层面

你会选择：

- 从头训练（Train From Scratch）
- Fine-tune
- Continual Learning

中的哪一种方案？

为什么？

**回答：**

我会优先选择 **Fine-tune**。

**原因：**
- 当前模型已经能识别锥桶，说明特征提取和检测框架是可复用的；
- Green Cone 与 Red / Orange Cone 在形状上非常相似，主要差异在颜色上，因此适合在现有模型上微调；
- 相比从头训练，Fine-tune 所需数据更少、收敛更快、上线周期更短；
- 如果后面还要新增更多锥桶颜色，可以在 Fine-tune 基础上继续做增量更新，必要时结合 continual learning 缓解灾难性遗忘。

---

#### 4. 训练层面

你会调整哪些训练参数？

例如：

- Learning Rate
- Batch Size
- Data Augmentation
- Loss Weight
- Class Weight

为什么？

**回答：**

- **Learning Rate**
  - 微调时学习率应比从头训练更小，避免破坏已有类别的能力；
  - 可使用 warmup + cosine decay，让训练更平稳。

- **Batch Size**
  - 受显存限制和数据量影响，选择合适的 batch size；
  - 若数据量较小，过大的 batch 可能导致泛化能力下降。

- **Data Augmentation**
  - 增加颜色扰动、翻转、缩放、仿射变换、亮度变化等；
  - 提升模型对不同拍摄条件的鲁棒性。

- **Loss Weight**
  - 如果 Green Cone 样本较少，可以适当提高它的损失权重；
  - 防止模型过度偏向已有的 Red / Orange 类别。

- **Class Weight / Sampling**
  - 对少样本类别进行过采样或加权；
  - 缓解类别不平衡问题，提高新类别召回率。

---

#### 5. 验证层面

如何验证新增类别不会影响已有类别效果？

你会关注哪些指标？

例如：

- Precision
- Recall
- mAP
- F1 Score

**回答：**

我会同时做“**新增类别验证**”和“**旧类别回归验证**”。

- **新增类别验证**
  - 重点看 Green Cone 的 Precision、Recall、AP、F1；
  - 确认新类别能否稳定识别。

- **旧类别回归验证**
  - 对 Red Cone、Orange Cone 等原有类别做同样测试；
  - 对比微调前后的 mAP、Precision、Recall，确保没有明显退化。

- **关注的指标**
  - **Precision**：看误报是否过多；
  - **Recall**：看漏检是否过多；
  - **mAP**：综合评估检测性能；
  - **F1 Score**：兼顾 Precision 和 Recall，适合衡量整体平衡；
  - 在线上还会关注误检率、漏检率和推理时延。

#### 关于 Recall
Recall（召回率）衡量的是：**真实存在的目标里，有多少被模型找出来了**。

可以简单理解为：
- Recall = 正确检出的目标数 / 真实目标总数

在这个题目里，如果新增 Green Cone 类别，Recall 低通常意味着：
- 绿色锥桶被漏检了
- 在逆光、遮挡、小目标情况下没有识别出来
- 模型更偏向旧类别，忽略了新类别

所以，验证新增类别时不能只看 Precision，更要重点关注 Recall。对于安全监控场景来说，漏检通常比误检更危险，因为漏掉真正的目标可能带来安全风险。

面试时可以这样回答：
> 我会重点关注新增类别 Green Cone 的 Recall，因为在安全监控场景里，漏检会直接影响风险识别的完整性。对于新增类别，通常需要先尽量保证召回，再结合业务容忍度，通过补充数据、调整阈值和优化后处理来逐步平衡 Precision 和 Recall。

#### 6. 部署层面

模型训练完成后：

如何部署到生产环境？

如果目标平台是：

- NVIDIA Jetson Orin

你会做哪些优化？

例如：

- TensorRT
- FP16
- INT8
- Batch Optimization

**回答：**

部署到 Jetson Orin 时，我会优先考虑模型加速和推理稳定性。

- **部署流程**
  1. 导出 ONNX 模型；
  2. 使用 TensorRT 构建推理引擎；
  3. 根据精度和速度需求选择 FP16 或 INT8；
  4. 接入视频流解码、推理和后处理模块；
  5. 在线监控延迟、吞吐量和误检漏检情况。

- **优化手段**
  - **TensorRT**：显著提升推理速度；
  - **FP16**：在精度损失较小的前提下加速推理；
  - **INT8**：进一步压缩和加速，但需要校准集；
  - **Batch Optimization**：如果有多路视频，可以做小批量推理提高吞吐；
  - **异步流水线**：将解码、推理、后处理分开，提高整体并发能力。

## 交付说明

### 颜色变换实现思路

在 `task1/data_color_aug.py` 中，采用 HSV 空间的 hue shift 思路，将红色锥桶的色相映射到绿色范围，从而生成绿色锥桶样本。相比直接在 RGB 空间做颜色替换，HSV 更适合做颜色迁移，因为色相、饱和度和亮度可以分开控制。

### 2^N 组合生成逻辑

将 N 种增强方式看作 N 个二值开关，每种增强都可以“启用/关闭”，因此组合总数为 `2^N`。脚本对每张输入图片先做颜色变换，再遍历所有增强组合，最终生成 `10 × 2^N` 张输出图。

### 运行结果

运行脚本后，`output_images/` 中的图片数量应满足预期，即：

- 输入 10 张图片
- N 种增强
- 输出总数 = `10 × 2^N`

## 总结

本题的核心是尽可能复用已有 YOLO 系统，通过少量真实数据 + 数据增强 + Fine-tune 的方式快速扩展出 Green Cone 检测能力。相比从头训练，这种方式成本更低、周期更短、上线更快，同时能够较好地保持原有红/橘色锥桶的检测效果。
