# 题目二：属性识别扩展

---

## 背景

公司目前已有一个基于 YOLO 的安全监控系统。

系统已经能够检测：

- Person
- Helmet
- Vest
- Vehicle

并已经完成训练和部署。

---

## 任务

客户提出第二个需求：

系统不仅需要识别人员，

还需要识别：

- 衣服颜色
- 安全帽颜色
- 是否穿反光背心

例如：

```yaml
Person:
  Helmet: Yellow
  Vest: Orange
  Clothes: Blue
```

---

### 请回答

你会如何设计系统？

**回答：**

我会把这个问题拆成“数据、标注、模型、推理、部署、业务规则”六个部分来设计。核心思路是：在保留现有检测能力的基础上，逐步增加属性识别能力，并保证线上实时性。

---

#### 数据采集

- 如何采集数据？
- 是否需要重新标注？

**回答：**

### 如何采集数据

我会采用“**增量采集 + 场景覆盖 + 长尾补齐**”的方式。

1. **复用现有检测数据**
   - 现有系统已经能检测 Person / Helmet / Vest / Vehicle，说明已有基础场景数据可复用。
   - 这些数据可以作为主体结构和目标尺度分布的基础。

2. **补充属性数据**
   - 新采集带属性信息的数据，重点覆盖：
     - 安全帽颜色：黄、红、白、蓝等
     - 工装颜色：蓝、灰、黑、橙等
     - 反光背心：是否穿戴、是否反穿、是否被遮挡
   - 尤其要补充“颜色接近背景”的样本，避免模型只学到单一颜色模式。

3. **覆盖真实复杂场景**
   - 白天 / 夜晚 / 逆光 / 阴影
   - 雨天 / 雾天 / 强光
   - 不同摄像头角度、不同焦距
   - 密集人群、遮挡、小目标、运动模糊

4. **长尾样本补齐**
   - 少见颜色
   - 半遮挡目标
   - 低清晰度目标
   - 反光背心被外套遮住的情况

### 是否需要重新标注

**需要。**

原因是原始标注只支持“目标类别检测”，而当前需求还需要“属性识别”，因此必须扩展标注信息。

建议新增以下属性字段：

- `helmet_color`
- `vest_color`
- `clothes_color`
- `has_reflective_vest`
- `wear_helmet`

标注时可采用“**目标框 + 属性标签**”的方式，把属性挂到 person 或相关目标上，方便后续模型训练和推理整合。

---

#### 标注方案

- 如何定义颜色类别？
- 如何保证标注一致性？

**回答：**

### 如何定义颜色类别

颜色不建议无限细分，否则会造成标注噪声大、类别边界模糊、训练困难。更合理的做法是将颜色离散化，例如：

- `white`
- `yellow`
- `orange`
- `red`
- `blue`
- `green`
- `black`
- `gray`
- `brown`
- `other`
- `unknown`

对于安全帽、马甲和工装，可以根据业务需要使用统一颜色集合，也可以针对不同属性定义独立标签集。

### 如何保证标注一致性

1. **制定统一标注规范**
   - 颜色以主体最明显区域为准
   - 遮挡严重时标为 `unknown`
   - 光照偏色时结合上下文判断

2. **建立样例图谱**
   - 给标注员提供颜色参考图，减少“红/橙”“蓝/灰”之类的边界混淆。

3. **双人标注 + 复核**
   - 关键样本采用双人交叉标注
   - 对冲突样本由仲裁人员最终裁定

4. **抽检与统计一致性**
   - 定期抽样检查
   - 对不同标注员的一致性做统计分析，持续修正规范

#### 模型结构

你会选择：

- 单模型方案
- 多模型方案
- Detection + Classification
- Multi-task Learning

为什么？

**回答：**

我会优先选择 **Multi-task Learning**，或者在工程初期采用 **Detection + Classification** 作为过渡方案。

### 推荐方案：Multi-task Learning

在共享 backbone 的基础上，同时输出：

- 检测框
- 类别
- 属性（颜色、反光、穿戴状态）

#### 优点
- 共享特征，计算效率高
- 推理速度快，适合实时监控
- 便于和现有 YOLO 系统集成
- 后续扩展属性更方便

### 备选方案：Detection + Classification

先用 YOLO 检测人、帽子、马甲，再对 ROI 做属性分类。

#### 优点
- 改造成本低
- 容易在已有系统上快速落地
- 适合做第一版上线

#### 缺点
- 推理链更长
- 额外计算量更大
- 检测误差和分类误差会串联传播

### 为什么不选单模型纯分类

因为单纯分类无法定位目标位置，不适合安全监控场景；而单纯检测又无法表达颜色、反光这类细粒度属性，因此需要引入属性头或分类分支。

---

#### 推理流程

推理阶段如何组织？

如何降低额外计算开销？

**回答：**

推荐推理流程如下：

1. 输入视频帧
2. YOLO 检测 person / helmet / vest
3. 对 person ROI 或关联目标做属性识别
4. 通过 `track_id` 做跨帧关联
5. 判断是否位于安全区域内
6. 根据业务规则触发告警

### 如何降低额外计算开销

1. **ROI 级属性识别**
   - 只对目标区域做分类，不做整帧重复推理。

2. **按 track 降频**
   - 对同一个人不必每一帧都识别属性，可以每 N 帧更新一次。

3. **时序平滑**
   - 利用跟踪结果和滑动窗口投票，减少属性闪烁。

4. **模型加速**
   - ONNX
   - TensorRT
   - FP16 / INT8
   - batch 推理

5. **异步流水线**
   - 解码、检测、属性识别、规则判断、告警上报拆成独立模块，提高吞吐。

---

#### 部署方案

如何保证实时性？

**回答：**

### 部署思路

建议采用边缘端推理 + 事件上报的方式：

- 在摄像头附近部署边缘设备，减少网络回传延迟
- 模块拆分为：视频解码、检测推理、属性识别、规则判断、告警上报
- 只上传违规事件和关键帧，不上传全量视频

### 实时性优化

1. **TensorRT 加速**
   - 将模型导出为 ONNX 后，使用 TensorRT 构建引擎。

2. **FP16 / INT8**
   - FP16 可在精度损失较小的情况下明显提速
   - INT8 在有校准集时可进一步压缩和加速

3. **Batch Optimization**
   - 多路视频时可采用小批量推理提升吞吐量

4. **异步处理**
   - 解码、推理、后处理并行运行，减少单点阻塞

5. **缓存与降频**
   - 对稳定 track 缓存属性结果，减少重复计算

| 字段 | 说明 |
|------|------|

### 2. 安全区域检测 Mock 函数

实现 `is_in_safety_zone()`（或等价函数），用于 debug：

- **输入**：工人检测结果（含位置、追踪 ID）、相机 ID、检测区域（多个点首尾连成的连通多边形）
- **输出**：工人是否在安全区域内（`True` / `False`）
- Mock 实现方式二选一或组合：
  - 直接返回固定或随机 `True` / `False`
  - 基于时间生成随机连续区段（模拟工人进出安全区域）

**回答：**

这样既可以做调试，也方便联调阶段验证业务逻辑。

### 3. 告警逻辑 Pipeline

`alert_pipeline.py` 或等价模块

- 从 **第一帧检测到违规** 到 **发出警报**，延迟 **不得超过 1 秒**
- 若违规行为 **持续存在**，应 **持续报警**
- 单个事件的报警消除后，进入 **5 秒 Cooldown**；Cooldown 期间不重复报警，直到 **新的危险** 再次出现

**回答：**

我实现了 `AlertPipeline.process_frame()`，满足以下业务逻辑：

- 如果检测到未佩戴安全帽，立即报警

- 违规全部消除后，进入 5 秒 cooldown
- cooldown 期间不重复报警
- 新危险再次出现后恢复报警

## 最终总结

本系统建议采用“**检测 + 属性识别 + 规则引擎**”的方案来扩展原有 YOLO 安全监控系统。  
在数据层，需要补充带属性标注的新数据；在模型层，优先采用多任务学习或检测加分类的方式；在部署层，通过边缘推理、ROI 分类、track 降频和事件驱动上报来保证实时性。  
业务端已实现告警 Pipeline，可满足“未佩戴安全帽”和“未穿指定颜色工装马甲且位于安全区域内”的违规判断需求，并支持首次告警、持续报警和 cooldown 机制。
